**문서 버전**: 1.0  
**최종 수정**: 2026-06-11  
**상태**: 설계 확정 / 구현 준비

## 1. 배경 및 목적

### 1.1 문제 정의

R&D 과제를 수행하는 연구자·연구행정 담당자는 다음과 같은 상황에 반복적으로 직면한다.

- 연구비 집행 항목이 허용 범위인지 즉시 확인이 어렵다
- 관련 법령(혁신법·시행령·시행규칙)과 공고문 조건이 상충하는 경우 어느 쪽이 우선인지 파악하기 어렵다
- 특허 출원, 인건비 처리, 외주 용역 등 타 법령(특허법·노동법 등)과 교차되는 질문은 담당자도 즉답하기 어렵다
- 전담기관·PM에 문의할 때까지 업무가 지연된다

### 1.2 목적

**실무 현장에서 즉시 사용할 수 있는 법령·규정 기반 자문 도구**를 제공한다.

- 근거 있는 정보만 답변 (검색된 법령·문서 외 추론 금지)
- 과제별 공고문·협약서를 최우선 근거로 활용
- 국가연구개발혁신법 생태계 + 타 법령(특허법·노동법 등) 통합 커버
- 판단 불가 시 어디에 문의해야 하는지 명확히 안내

### 1.3 주요 사용자

| 역할 | 주요 니즈 |
|---|---|
| 연구행정 담당자 | 연구비 집행 허용 여부, 정산 기준, 규정 확인 |
| 연구책임자 | 인건비·장비비 기준, 과제 변경 절차 |
| 연구원 | 학생인건비, 출장비, 특허 관련 권리 |

## 2. 제품 개요

### 2.1 핵심 컨셉: 과제 컨텍스트 기반 챗봇

기존 context-free 챗봇의 한계를 극복하기 위해, **세션을 특정 과제에 묶어** 모든 질문을 해당 과제의 사업 유형·기관·공고문 조건 안에서 처리한다.

```
[기존]  질문 → 도메인 추측 → 소스 선택 → 답변
[목표]  과제 등록 → 질문 → 컨텍스트 기반 검색 → 답변
```

### 2.2 핵심 가치

1. **정확성**: 법령 원문 + 공고문 조건의 교차 확인
2. **신뢰성**: 모든 답변에 출처(문서명·조문·페이지) 명시
3. **범용성**: 혁신법 생태계 외 특허법·노동법 등 타 법령 커버
4. **실무성**: 판단 불가 시 문의처(전담기관·PM) 명확 안내

## 3. 기능 요구사항

### 3.1 과제 관리 (신규)

#### 3.1.1 과제 등록

| 필드 | 타입 | 비고 |
|---|---|---|
| 과제명 | 텍스트 | 필수 |
| 사업 유형 | 선택 | 중소기업기술개발 / 기초연구 / 산업기술 / IITP / NRF / KIAT / 기타 |
| 기관 유형 | 선택 | 대학 / 출연연 / 기업 / 병원 / 기타 |
| 전담기관 | 선택 | IITP / NRF / KIAT / KOITA / 기타 |
| 과제 단계 | 선택 | 착수 / 진행중 / 종료 |
| 과제 기간 | 날짜 | 시작일 ~ 종료일 |

#### 3.1.2 과제 문서 관리

- 공고문 / 협약서 / 내부규정 / 기타 PDF 업로드
- 업로드 즉시 자동 인덱싱 (Qdrant, 과제 ID 태그)
- 문서별 인덱싱 상태 표시 (대기 / 완료 / 실패)
- 문서 삭제 시 Qdrant 청크 동시 삭제

#### 3.1.3 과제 목록 및 전환

- 등록된 과제 목록 표시 (최근 활성 순)
- 과제 전환 (사이드바에서 즉시 변경)
- 과제 수정 / 삭제

### 3.2 챗봇 (기존 기능 확장)

#### 3.2.1 과제 컨텍스트 의존

- 활성 과제 없이 질문 불가 (과제 등록 유도 화면 표시)
- 챗봇 상단에 현재 과제명 + 업로드 문서 현황 표시
- 과제 전환 시 대화 히스토리 초기화 여부 선택

#### 3.2.2 검색 우선순위 (고정)

```
1순위: 과제 공고문·협약서 (Qdrant, project_id 필터)
2순위: 혁신법·시행령·시행규칙·매뉴얼 (Qdrant, builtin)
3순위: 법제처 MCP + 국가법령정보 공동활용 API (병렬, 항상 실행)
         ├─ 법령 (모든 현행 법률)
         ├─ 판례
         ├─ 행정규칙 본문 (훈령·예규·고시)
         └─ 법령해석례 (법제처 공식 해석)
```

도메인 분류 없이 우선순위 고정. 타 법령(특허법·노동법 등)은 3순위 외부 API가 자동 커버.

#### 3.2.3 답변 구조

```json
{
  "verdict": "가능 | 불가 | 조건부 가능 | 판단불가",
  "summary": "결론 및 근거 요약",
  "citations": [
    {
      "document_name": "출처 문서명",
      "article_no": "조문 번호",
      "page": 0,
      "quote": "원문 발췌 50자 이내"
    }
  ],
  "follow_up_needed": true,
  "follow_up_questions": ["확인 필요 사항"],
  "risk_notes": ["주의사항"]
}
```

#### 3.2.4 질의 유형 지원

| 유형 | 예시 | 처리 방식 |
|---|---|---|
| 판단형 | "학생인건비로 노트북 살 수 있어?" | verdict + 근거 |
| 조문 조회 | "혁신법 제15조 내용은?" | 전문 출력 |
| 페이지 조회 | "매뉴얼 151p 내용" | 페이지 직접 읽기 |
| 비교형 | "종전 vs 혁신법 달라진 점" | 표 형식 비교 |
| 공고문 확인 | "이 사업 직접비 한도는?" | 1순위 공고문 검색 |
| 타 법령 | "연구원 주52시간 적용되나?" | 외부 API 노동법 |
| 일상 대화 | "안녕하세요" | 즉답 (검색 스킵) |

### 3.3 비기능 요구사항

| 항목 | 기준 |
|---|---|
| 답변 소요 시간 | 일반 질의 60초 이내, 페이지/조문 조회 120초 이내 |
| 인용 의무 | 모든 답변에 출처 1개 이상 필수 |
| 근거 외 추론 | 금지 — [검색된 근거]에 없는 내용 추정 불가 |
| 오프라인 동작 | Qdrant + 로컬 인덱스 기반 (외부 API 실패 시 graceful 폴백) |

## 4. 시스템 아키텍처

### 4.1 전체 구조

```
사용자 질의
  └─ query_analyzer (Claude Haiku)
       ├─ kind: chat / page_lookup / article_lookup / comparison / open
       └─ rewritten_query (멀티턴 컨텍스트 흡수)

              │
              ├─ [1순위] Qdrant — 과제 공고문·협약서
              │           filter: project_id = 활성 과제
              │
              ├─ [2순위] Qdrant — 혁신법 생태계 built-in
              │           filter: source = "builtin"
              │
              └─ [3순위] 외부 법령 (병렬)
                   ├─ 법제처 MCP (korean-law-mcp)
                   └─ 국가법령정보 API (law.go.kr/DRF)
                        ├─ 법령·시행령·시행규칙
                        ├─ 판례
                        ├─ 행정규칙 본문
                        └─ 법령해석례

              → generate_answer (Claude Sonnet 4.6)
                   ├─ 기본 모델: Sonnet 4.6
                   ├─ 비교형: Opus escalate
                   └─ 과제 컨텍스트 블록 시스템 프롬프트 주입
```

### 4.2 Qdrant 스키마

단일 컬렉션 `rnd_law_chunks` — 페이로드 필드:

| 필드 | 값 | 설명 |
|---|---|---|
| `source` | `"builtin"` | 혁신법 생태계 (기존) |
| `source` | `"project"` | 사용자 업로드 문서 |
| `project_id` | UUID | 과제별 필터링 (`source=project`에만) |
| `doc_type` | 문자열 | 공고문 / 협약서 / 법률 / 시행령 / 매뉴얼 등 |
| `doc_name` | 문자열 | 출처 문서명 |
| `article_no` | 문자열 | 조문 번호 (없으면 빈 문자열) |
| `page` | 정수 | PDF 페이지 번호 |
| `text` | 문자열 | 청크 본문 |

### 4.3 과제 데이터 저장

`data/projects.json` — 로컬 JSON (Qdrant 벡터와 별도):

```json
{
```

## 7. 구현 단계

### Phase 1 — 데이터 기반 (1~2일)
- `project_store.py`: 과제 CRUD, JSON 저장
- `indexer.py`: `project_id` + `source` 페이로드 스키마 추가
- 기존 built-in 청크에 `source="builtin"` 일괄 태그 (재인덱싱)

### Phase 2 — 파이프라인 연결 (2~3일)
- `prompts.py`: 과제 컨텍스트 블록 생성 함수
- `app.py` `run_pipeline`: 컨텍스트 주입 + 3단계 검색 라우팅
- `answer_cache.py`: `project_id` 캐시 키 추가
- `query_analyzer.py`: `domain` 제거, 시스템 프롬프트 일반화

### Phase 3 — UI (2~3일)
- `pages/01_📁_과제관리.py`: 과제 등록·수정·문서 업로드 화면
- `app.py` 사이드바: 과제 선택 컴포넌트, 미선택 시 가드
- 챗봇 상단 과제 컨텍스트 표시

## 8. 제약 및 한계

| 항목 | 내용 |
|---|---|
| 공고문 미업로드 | 업로드하지 않으면 3순위 외부 API만으로 답변 — 과제별 특수 조건 미반영 가능 |
| 외부 API 의존성 | 법제처 MCP / 국가법령정보 API 장애 시 로컬 인덱스로만 답변 |
| 법적 효력 | 이 챗봇의 답변은 참고용이며, 최종 판단은 전담기관·PM 확인 필요 |
| 비공개 내부 규정 | 사용자가 직접 업로드해야 커버 가능 |
| 최신 법령 반영 | 국가법령정보 API는 실시간, 로컬 인덱스는 수동 동기화 필요 |

## 9. 용어 정리

| 용어 | 설명 |
|---|---|
| 과제 컨텍스트 | 활성 과제의 사업 유형·기관·전담기관·업로드 문서 묶음 |
| built-in 청크 | 시스템에 사전 인덱싱된 혁신법 생태계 문서 청크 |
| project 청크 | 사용자가 특정 과제에 업로드한 PDF의 청크 |
| 전담기관 | 과제를 관리하는 기관 (IITP, NRF, KIAT 등) |
| verdict | 챗봇이 내리는 최종 판단 (가능/불가/조건부 가능/판단불가) |
| Phase H | 페이지·조문 직접 조회 도구 모드 (read_page / get_article) |
